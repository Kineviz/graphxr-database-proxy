# 嵌入式数据库：Kuzu、Ladybug 与 LatticeDB

它们都是嵌入式图数据库：项目指向的是**代理机器上的一个文件**，而不是一台服务器。没有主机、
没有端口、没有密码——访问控制就是文件系统本身。

它们是两个家族，不是三个。

**Kuzu 和 Ladybug 是同一个引擎的两个名字。** Ladybug 是 Kuzu 分叉之后的延续，用同一套
Cypher、同一套 catalog，但写入的魔数不同，存储格式也是另一条序列，所以一个库只属于其中
一个家族。

**LatticeDB 是另一个独立项目。** 它同样是嵌入式、同样说 Cypher，相似之处也就到此为止：
文件格式不同、语法更窄、完全没有 schema，而在最关键的地方——身份标识——它反而比前两者更好。
详见 [GraphXR 能拿到什么](#graphxr-能拿到什么)。

> **LatticeDB 没有发布 Windows 轮子。** 在 Windows 上需要自己编译一次——引擎在那里跑得
> 很好，卡住的是**打包**，只发到了 Linux 和 macOS。见
> [自己编译引擎](#自己编译引擎)；不想编译就用 Docker 镜像或 Linux / macOS 主机。
> Kuzu 和 Ladybug 不受影响。

**在 Kuzu 家族内部，项目类型不必和文件对上。** 选了 Kuzu 的项目指向一个 Ladybug 库时，会自动改用 Ladybug 的
依赖包和 Ladybug 的版本序列去处理；反过来同理。两者本来就是同一份代码的两个名字——语句相同、
catalog 相同、结果形状相同——所以在这里报错，等于把一个本来能正常服务的库变成配置错误。
项目类型决定 URL（`/api/kuzu/...` 还是 `/api/ladybug/...`）和界面上的名字，文件决定引擎。

这个替换不会悄悄发生：配置时表单会明确写出来，`GET /api/{type}/{project}` 也会在
`features.engine` 里报告实际使用的引擎。

有一点需要知道：**当文件属于另一个家族时，Engine version 的锁定会被丢弃**。`0.11` 是
Kuzu 的版本线，Ladybug 没有 0.11；把它带过去只会把一个能用的库变成一次失败的安装。

**这种替换不会跨到 LatticeDB。** `latticedb` 项目指向 Kuzu 或 Ladybug 的库会被直接拒绝，
反过来同理。LatticeDB 打不开那些库；即便打得开，代理为它生成的语句也不是 Kuzu 的那套。
所以这里会明确告诉你这个文件应该用哪种项目类型，而不是悄悄换一个引擎去服务它。

## 简要流程

1. 新建项目，数据库类型选 **Kuzu (embedded)**、**Ladybug (embedded)** 或
   **LatticeDB (embedded)**。
2. 填写路径，或者把库文件拖到表单上。
3. 代理读取文件头，算出能打开它的引擎版本；本地没有就自动下载，表单上会显示进度。
4. 让 GraphXR 指向 `/api/kuzu/<project>`、`/api/ladybug/<project>` 或
   `/api/latticedb/<project>`。

## 为什么由文件决定引擎版本

每个库的开头都是 4 个魔数字节（标明家族），紧跟着 **storage version**——磁盘格式号：

```
4b 55 5a 55  27 00 00 00 00 00 00 00     KUZU，格式 39   (Kuzu 0.11.x)
4c 42 55 47  2b 00 00 00 00 00 00 00     LBUG，格式 43   (Ladybug 0.19.x)
42 44 54 4c  03 00 03 00 00 10 00 00     BDTL，格式 3    (LatticeDB 0.9+)
```

Kuzu 和 Ladybug 把格式号写成 64 位；LatticeDB 写的是 16 位，而且**写两遍**——它写入时用的
格式，以及允许读取它的最低版本——再往后的字节是页大小，不是版本号的一部分。LatticeDB 至今
用过三种格式：1（0.2–0.4）、2（0.5–0.8）、3（0.9 起）。

决定哪个引擎版本能读这个库的，是这个数字——不是文件名，也不是某个配置项。Kuzu 只接受
与自己完全一致的格式；Ladybug 和 LatticeDB 则各自能接受比自己低的一段范围。用错误的版本打开会失败，而且
失败得很难看——Kuzu 0.10 打开 0.11 的文件，会从 catalog 读取器深处抛出
`UnicodeDecodeError`——所以代理自己先读文件头、自己挑版本，而不是把路径交出去碰运气。
如果这个路径根本不是一个库，才会在这一步被拒绝，并告诉你读到的是什么。

格式号到发布版本的映射，是**以格式号为键**的，而不是以版本线为键。这正是"忽略小版本号"
自然成立的原因：0.19.0 和 0.19.1 都写格式 43，所以一个格式 43 的库会拿到其中最新的那个；
等 0.19.2 发布那天，代理不用改任何代码就会自动用上它。

代理内置的对照表覆盖今天已存在的所有版本，因此离线也能解析。Kuzu 和 Ladybug 的部分抄自
两个项目自己的 `storage_version_info.h`；LatticeDB 没有公布这样的文件，所以它那部分是**实测**
出来的——每个版本装一遍、建一个库、读它的头部字节。在此之上
它会**自己学**：加载过的版本会被问"你写哪个格式"，成功打开过某个库的版本会被记下"能读这个
格式"，打开失败的则被取消记录。学到的内容保存在 `config/engine_versions.json`。如果遇到
比它已知的都新的格式，它会去 PyPI 列出发布版本，装最新的少数几个，探测出到底是哪个写的。

## 引擎装在哪里

每个发布版本单独安装在 `~/.graphxr-proxy/engines/` 下，并且运行在**自己的进程**里。这不是
洁癖：在已经 import 过 `ladybug` 的进程里再 import `kuzu` 会直接失败——两者都是 pybind11
扩展，抢注同一批类型名——所以一个同时服务 Kuzu 项目和 Ladybug 项目的代理，自己一个引擎都
装不下。

LatticeDB 是另一条路走到同一个结论。它是 `ctypes` 绑定，没有类型注册表可以撞；但它的动态库
是**从自己的包目录里**加载的，所以两个版本就意味着一个解释器里要有两个 `latticedb` 包。
「按版本各自安装 + 单独进程」是这里每个引擎都需要的，只是各有各的理由。

必要时引擎还会用**自己的解释器**。比如 `kuzu` 0.11.3 在 Windows 上没有 CPython 3.14 的
轮子；如果代理跑在 3.14 上，就用 `uv` 拉一个 3.13 给引擎用，代理自己不动。安装并不以"文件
落盘"为完成标志，而是以"引擎真的启动过一次并应答"为准——轮子标签匹配不代表能加载成功——
如果跑不起来，就换计划里的下一个解释器。

因此**强烈建议安装 `uv`**。没有它，代理只能为自己的解释器安装；装不了时它会告诉你哪些
解释器版本可行，而不是去尝试源码编译。

## 自己编译引擎

引擎得为你的平台发布轮子，而其中一个没有。LatticeDB 是 Zig 项目，上游 CI 没有 Windows
任务，所以 Windows 上 PyPI 只有源码包——而它自己编译不了自己，因为 `setup.py` 要加载的
构建脚本并不在源码包里。Kuzu 和 Ladybug 不受影响。

引擎本身在 Windows 上没问题。一条命令就能交叉编译出来，而且它在 Windows 上写出的库，文件头
和格式号与 Linux 上写出的完全一致，库文件可以直接互换。缺的只是"把编译结果交给代理"的途径。

放进 `~/.graphxr-proxy/wheelhouse/` 的任何轮子就是这条途径。它会加入安装器考虑的发布版本
列表，像已发布的轮子一样按本机标签做匹配，并且**按路径安装**——所以你自己编的那份会直接
胜过 PyPI 上同版本的文件，而不是和它抢。轮子自身的依赖仍然正常解析。同一套机制也适用于
离线（内网）安装，三个引擎都适用。

在 Windows 上编译 LatticeDB 轮子需要 [Zig](https://ziglang.org) 0.16 或更新：

```powershell
git clone https://github.com/jeffhajewski/latticedb
cd latticedb
zig build shared -Doptimize=ReleaseFast     # -> zig-out\bin\lattice.dll

pip install build wheel
cd bindings\python
$env:LATTICE_BUNDLE_LIB_PATH = "..\..\zig-out\bin\lattice.dll"
python -m build --wheel
wheel tags --platform-tag=win_amd64 --remove (Get-ChildItem dist\*.whl).FullName

mkdir -Force ~\.graphxr-proxy\wheelhouse
copy dist\latticedb-*-win_amd64.whl ~\.graphxr-proxy\wheelhouse\
```

有两个细节容易漏。Windows 把 DLL 留在 `zig-out\bin\`，而不是其它平台的 `zig-out\lib\`。
另外重打标签不是走形式：这个包是纯 Python 的，直接构建会打成 `py3-none-any`，可它里面装着
一个 Windows DLL——"哪里都能跑"恰恰是这个轮子唯一做不到的事。

之后照常配置 LatticeDB 项目即可。下一次连接就会从 wheelhouse 安装，而不再报平台缺口。

依赖它之前有两点要知道。上游没有 Windows CI，后续版本在 Windows 上出问题不会有人发现，
这份验证得你自己来。另外多跳的限制来自引擎而不是平台——它在所有操作系统上都声明为不支持，
原因相同。

## 项目配置项

| 字段 | 含义 |
|---|---|
| **Database path** | 库的位置。Kuzu 0.11+ 与所有 Ladybug、LatticeDB 版本是单个文件；Kuzu 0.10 及更早写出的是**目录**。这个字段会把代理已有的库列出来（见下），同时仍然接受任意手输路径。 |
| **Engine version** | 一般留空，由文件决定。填 `0.19` 表示锁定到最新的 0.19.x；填 `0.19.1` 表示锁死这个版本。 |
| **Access** | 默认只读。 |

路径字段既是输入框也是下拉框。它会列出文件库里的库、以及其它项目已经指向的路径，每一条都标着从
文件头读出来的引擎和版本——所以复用一个库是**选**出来的，而不是回忆它放在哪儿。它只列前一百条，
并会写明还有多少条没列出来；代理磁盘上任何其它位置的库依然是有效答案，手输完整路径即可。

**默认只读是有原因的。** 代理本来就是读路径，而只读打开是可以共享的——包括你自己的工具在内，
多个进程可以同时打开这个库。可写的项目会独占该文件，代理持有期间别的进程都打不开。

### 拖拽上传

拖放区会把文件复制到代理的 `config/databases/<project>/<filename>`，并自动填好路径。文件在
上传过程中就被校验，一旦头部字节表明它不是库就立即拒绝，所以一个很大的错误文件不会被完整
写完。如果同名文件已经存在，会先询问再覆盖。

**Kuzu 0.10 及更早的库是目录**而不是文件，因此无法拖拽。请直接在输入框里填路径，代理会从
目录里的 `catalog.kz` 读取文件头。Ladybug 和 LatticeDB 的每个版本写的都是单个文件。

## 文件库

所有拖上来的文件都落在同一个地方，**Files** 页面就是这个地方：`config/databases`，并把每个文件
到底是什么列出来。

每一行都带着从文件本身读出来的引擎与存储格式、能打开它的版本以及该版本是否已安装、文件大小，
还有**哪些项目正指向它**。最后这一列才是这个页面存在的理由。库可以在这里删除，而**仍被项目引用的
库第一次会被拒绝**，并在提示里写出那些项目名——否则的话，项目会一直「正常」到下一次 GraphXR
打开它为止。

关于它展示的内容，有三点值得说明：

- **代理服务不了的文件照样列出来。** 目录里的 SQLite / DuckDB 文件会被如实命名，而不是标成
  「无法识别」，更不是直接隐藏。它本来就躺在磁盘上，而一个只显示自己看得懂的东西的列表，正是
  目录里堆满没人找得到的文件的原因。这两者目前都没有驱动，所以都不能用来建项目；上传仍然只接受
  Kuzu、Ladybug 和 LatticeDB，按头部字节拒绝其余。
- **目录布局的库是一行，不是一个文件夹。** 带 `catalog.kz` 的目录是 Kuzu 0.10 及更早的库，页面把它
  作为单独一条列出，删除时整体删掉。
- **列表在代理侧分页。** 每一行都要读一次文件头，所以一页十条就是读十个文件，而不是把目录里所有
  文件都打开一遍。删掉文件夹里最后一个库时，文件夹会一并删除。

行上的 **Create project** 会打开项目表单，路径已填好，类型设成写这个文件的那个引擎。在 Kuzu
家族内部两种类型其实都能用——引擎由文件决定——但直接开在对得上的那个上，能省掉一次改动。
对 LatticeDB 的库来说，对得上的类型是**唯一**能启动的那个。

## GraphXR 能拿到什么

三者都提供图接口：`/query`、`/schema`、`/graphSchema`、`/sampleData`、`/capabilities`、
`/expand`、`/pullCategory`、`/pullRelationship`。两个家族之间的差异值得了解。

|  | Kuzu / Ladybug | LatticeDB |
|---|---|---|
| 节点 id | `<Label>:<主键>` | 引擎自己的整数 |
| expand 重新选中种子靠 | 主键属性 | 身份标识（`id(n)`） |
| 按 id 排除某条边 | 不支持 | 支持 |
| 把遍历两端都钉住 | 不支持 | 支持 |
| 多跳 expand | 支持 | 不支持——见下 |
| `/schema`（关系型视图） | 支持，来自 catalog | 不支持，没有任何声明 |
| `/graphSchema` | 从 catalog 读 | 采样推断 |
| 全文检索 | 未接入 | 未接入 |

### Kuzu 与 Ladybug

**节点 id 是 `<Label>:<主键>`。** 这两个引擎有 `ID(n)`，但没有办法把它作为字面量写回语句里，
所以内部 id 一旦发出去就再也匹配不回来。而节点表**必须**有主键——不带主键声明的建表语句直接
是语法错误——所以这个形式总是存在；主键是哪一列，代理直接从 catalog 读，不靠猜。

**这里的 `/schema` 是真能回答的。** Kuzu 的表是有声明的，所以关系型视图能报出真实的列类型；
Neo4j 与 Memgraph 的驱动在这个接口上只能拒绝。

### LatticeDB

**节点 id 就是引擎自己的整数**，因为这里的 `id(n)` 既能读出来、**也能匹配回去**——
`WHERE id(n) IN [1,2]` 是合法的。仅此一点就拓宽了整个能力面：种子按身份标识重新选中、
边可以按 id 排除、遍历的两端都能钉住。这些 Kuzu 一个都做不到。

**`/graphSchema` 是推断出来的，不是读出来的。** LatticeDB 的节点在创建时既不声明标签也不声明
属性，所以根本没有 catalog 可问。代理先问「有哪些不同的标签」和「有哪些不同的（起点标签,
关系类型, 终点标签）三元组」，再按每个类别采样有限条节点、看它们带哪些属性，类型则从值上推断。
因此这个 schema 是**对采样结果的描述**：某个只出现在该类别第一万个节点上的属性，不会出现在里面。

**`/schema` 会拒绝**，和 Neo4j、Memgraph 一样，理由也一样——没有关系型结构可以报告。

**不提供多跳 expand**，而且不是因为语法不支持：链式模式能解析、也能正确返回结果。问题在于
这个后端所需的投影**每多一跳就多八列**——它的边不携带端点，所以每条边的两端都得写进 `RETURN`
——而在这个宽度上，latticedb 0.14.0 会破坏内存并让引擎进程直接崩溃。单跳是稳定的，客户端
可以一跳一跳地走出去。

**它没有引用标识符的语法。** 反引号出现在任何位置都是 `Invalid token`——label、
关系类型、属性名、变量都一样——而且没有替代品：双引号和方括号在这些位置同样被拒绝。其它
Cypher 后端都接受反引号，所以习惯性加引号的客户端发过来的语句，这个引擎连读都读不下去就
拒掉了；GraphXR 的搜索构建器就会给每个 label 和每个关系类型都加上反引号。代理会把本来就是
裸标识符的名字上的反引号去掉。而**不是**裸标识符的名字——比如带空格的 label——在模式里根本
无处安放，于是改为搬进 `WHERE` 谓词：`MATCH (n0:`Order Item`)` 变成
`MATCH (n0) WHERE "Order Item" IN labels(n0)`，和 dialect 给自己语句生成的写法一致。
原有的 `WHERE` 条件会先加括号，再和新谓词用 `AND` 连接。

**手写的 `/query` 在能读懂时会被改写。** LatticeDB 的语法里没有 `*`，所以
`MATCH (n)-[r]->(m) RETURN * LIMIT 100`——几乎每个人第一句都这么写——会直接卡在语法分析上，
报 `Expected expression`。改成点名变量更糟：它根本没有节点或关系这种值类型，所以
`RETURN n, r, m` 能解析，返回的却是三个整数——既不是报错，也不是图。代理会把这两种写法都
改写成它自己语句所用的投影，结果按图返回。

它只改写自己能读懂、不需要猜的那些：一个 `MATCH`、没有任何会重新绑定变量的子句、`RETURN`
是 `*` 或模式里绑定过的裸变量名，并且每条被投影的关系都是有向的、两端都有具名节点。无向的
`(n)-[r]-(m)` 会被拒绝而不是硬处理——边本身问不出自己的两端，端点只能来自模式，而这个模式
并没有说清边到底朝哪个方向。读不懂的语句会原样交给引擎；如果它随后因为缺少 `*` 而失败，
错误信息里会带上原因，并给出应该改写成什么样的投影示例。而 intent 接口完全不经过这一套——
它本来就按正确方式投影。

三者都不提供全文检索。Kuzu 和 Ladybug 有全文扩展但还没接上。LatticeDB 内置了 BM25——这里唯一
一个自带全文的引擎——但它的索引需要逐个节点显式调用去填充，所以一个没人建过索引的库，任何
搜索都只会返回空。两种情况下能力声明里都如实写了不支持，而不是给客户端一个背后没有实现的按钮。

| `GRAPHXR_PROXY_ENGINE_MAP` | `config/engine_versions.json` | 学习到的"格式号 → 发布版本"映射存放位置。 |
| `GRAPHXR_PROXY_STORES_DIR` | `config/databases` | 文件库：拖拽上传的库存放位置，也是 Files 页面列出的目录。 |

| `GRAPHXR_PROXY_WHEELHOUSE` | `~/.graphxr-proxy/wheelhouse` | 你自己编译的轮子，优先于 PyPI。 |

## 出问题时

**"does not start with an embedded-store magic number"** —— 这个路径不是一个库。如果它是
目录，检查里面有没有 `catalog.kz`。

**"is a Kuzu store, not a LatticeDB store"** —— 项目类型和文件跨了家族边界，而代理在这条
边界上不做替换。提示里会写明应该改用哪种项目类型。

**"latticedb 0.14.0 publishes no wheel for this platform at all"** —— 你在 Windows 上。
LatticeDB 只发布 macOS 和 manylinux 轮子，这台主机上没有任何解释器能装上它，换 Python 版本
没有用。自己编译一次即可，见 [自己编译引擎](#自己编译引擎)；也可以改用 Docker 镜像或
Linux / macOS 主机。报错信息里会写明它会从哪个 wheelhouse 目录安装。

**"No kuzu release is known to read storage version N"** —— 这个格式比代理能找到的任何版本
都新。`GET /api/embedded/known-formats` 会列出它已知的格式。没有网络的代理无法发现它发布之后
才出现的引擎版本。

**"publishes no wheel for CPython 3.x on this platform"** —— 安装 `uv`，让代理可以给引擎单独
准备一个解释器；或者把代理换到消息中列出的解释器版本上运行。

## 跑真实引擎的测试

测试套件默认离线，引擎是打桩的。要跑真引擎：

```bash
GRAPHXR_PROXY_ENGINE_TESTS=1 uv run pytest tests/test_embedded_integration.py -q
```

它会下载引擎，首次运行建议把 `GRAPHXR_PROXY_ENGINES_DIR` 指到一个可以随手删掉的目录。
